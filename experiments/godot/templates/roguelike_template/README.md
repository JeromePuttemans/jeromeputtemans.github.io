# Roguelike — Algorithmic Principles

## What is a roguelike?

A roguelike is a genre defined by a specific combination of constraints: turn-based
movement on a discrete grid, procedurally generated levels that reset on every run,
and permanent death. The name comes from the 1980 game Rogue. Every mechanic in the
genre exists in service of three design goals: each run must feel meaningfully different,
every decision must have permanent consequences, and the world must feel alive despite
having been generated by an algorithm minutes ago.

Understanding this genre means understanding five core algorithmic problems:
how to generate a connected dungeon, how to compute what the player can see,
how to sequence actions in time, how to make enemies feel purposeful,
and how to represent spatial relationships efficiently.

---

## 1. Procedural Dungeon Generation — the random room placement algorithm

The minimal dungeon generation algorithm has three steps.

**Step 1: Place rooms without overlap.**
Each room is a random-sized rectangle. Before placing it, the algorithm checks it
against every already-placed room. If they intersect (with a one-tile buffer),
the placement attempt is discarded. The loop runs for a fixed number of attempts:

```
for i in max_rooms:
	room = random_rect()
	if no overlap with existing rooms:
		carve room into the grid
```

**Step 2: Connect rooms with L-shaped corridors.**
Each new room is connected to the previous one. The corridor consists of two
segments: a horizontal run from the center of room A to the x-coordinate of
room B's center, then a vertical run completing the connection. This algorithm
guarantees full connectivity — every room is always reachable from every other.

```
carve_horizontal(center_A.x → center_B.x, at y = center_A.y)
carve_vertical(center_A.y → center_B.y, at x = center_B.x)
```

**Step 3: Assign semantic positions.**
The player starts at the center of `rooms[0]`. Stairs are placed at the center
of the last room placed (the one farthest from the start in placement order).
Enemies are spawned in all rooms except `rooms[0]`, preventing unfair starts.

The resulting dungeon is always connected, always has a clear start-to-goal path,
and looks different on every run. Its weakness is that corridors occasionally
overlap rooms, creating open areas — a property many players enjoy.

## 2. Field of Vision — Bresenham raycasting

The FOV system answers the question: which tiles can the player currently see?
This matters for gameplay (enemies outside FOV don't act on the player)
and for atmosphere (unexplored areas stay dark).

**The raycasting algorithm:**
For every tile within Euclidean distance `r` of the player:
1. Cast a ray using Bresenham's line from the player to the target tile.
2. Walk each cell along the ray (excluding origin and target).
3. If any intermediate cell is a WALL, the target is not visible.
4. Otherwise, the target is visible — even if it IS a wall (you see its face).

```
for each tile T within radius r:
	line = bresenham(player, T)
	if no wall in line[1..n-2]:
		T is visible
```

**Bresenham's line** produces integer grid cells along a line between two points,
with no gaps and no diagonal jumps. It uses an error accumulator to decide at each
step whether to advance horizontally, vertically, or both:

```
err = dx + dy    # dy is negative
while not at target:
	e2 = 2 * err
	if e2 >= dy: err += dy; x += step_x
	if e2 <= dx: err += dx; y += step_y
```

**The two-layer visibility model:**
- `visible[x][y]` — currently in FOV (recomputed every turn)
- `explored[x][y]` — ever seen (persistent, merged from visible each turn)

Explored but not currently visible tiles are drawn in a dimmed color. This is
the "fog of war" mechanic: the player remembers the layout but not the current
state (enemies may have moved).

**Complexity and tradeoffs:**
O(r²) tiles × O(r) ray steps = O(r³). With r=8: ~1600 operations per turn,
negligible on modern hardware. The tradeoff versus shadowcasting algorithms
(which are O(r²)) is that raycasting allows "corner peeking" through diagonal
wall pairs. This is the standard pedagogical tradeoff for this template.

## 3. The Turn System — discrete time as a state machine

A roguelike game loop is not continuous — it is event-driven. Time passes in
discrete turns, not in frames. The state machine has four phases:

```
PLAYER → (player acts) → ENEMY → (all enemies act) → PLAYER
PLAYER or ENEMY → GAME_OVER  (if player HP reaches 0)
PLAYER → VICTORY             (if player descends past the final floor)
```

**Player turn processing** (`player_action(direction)`):
1. Validate the action is legal in the current phase.
2. Resolve the action (move, attack, or wait).
3. Transition to ENEMY phase.
4. Process all enemies.
5. Transition back to PLAYER phase.
6. Emit `turn_ended` to trigger UI updates.

**The bump-to-attack mechanic:**
The player does not have a separate "attack" command. Attempting to move into
a cell occupied by an enemy triggers combat instead. This unifies the movement
and combat input into a single key, keeping the interface minimal.

```
new_pos = player.pos + direction
if enemy at new_pos: attack enemy
else if walkable:    move to new_pos
else:                do nothing (wall bump — does not consume the turn)
```

**Turn consumption:**
Not all inputs consume a turn. Bumping into a wall is free — it would be frustrating
to have enemies act every time the player presses the wrong key. Only valid actions
(movement, attack, wait) advance the turn counter.

## 4. Enemy AI — greedy chase with proximity attack

The minimal enemy AI makes enemies feel threatening without implementing
full pathfinding. Each enemy independently executes this algorithm:

```
dist = chebyshev(enemy.pos, player.pos)
if dist == 1:           attack player
if dist > chase_range:  idle
else:                   move one step toward player
```

**Chebyshev distance** (`max(|dx|, |dy|)`) is the "chessboard distance" where
diagonal moves are free, matching the movement model of the game. It is the
correct metric for this grid topology — not Euclidean, and not Manhattan.

**The greedy step:**
The preferred move is the diagonal step that reduces both dx and dy simultaneously.
If that cell is blocked, the algorithm tries the horizontal step, then the vertical:

```
candidates = [(dx, dy), (dx, 0), (0, dy)]   # when both dx,dy ≠ 0
for pos in candidates:
	if walkable and no enemy and not player's cell:
		move there and stop
```

This heuristic works well in open rooms but fails in corridors where enemies
block each other. The fix is A* pathfinding, which is the natural next extension.

**Chase range as a design parameter:**
Different enemy types have different `chase_range` values. A rat (chase_range=6)
ignores the player from across a large room, creating safe exploration zones.
A troll (chase_range=10) hunts relentlessly across most of the FOV radius.
This single parameter creates dramatically different encounter dynamics.

## 5. Spatial Indexing — the enemy position dictionary

Naively checking whether a cell is occupied requires iterating all enemies: O(n).
During enemy turn processing, this would make move validation O(n²).
The solution is a spatial index: a Dictionary mapping each occupied position
to the entity there.

```
enemy_positions: Dictionary = {}   # { Vector2i: EnemyEntity }
```

Every move updates the index:
```
enemy_positions.erase(old_pos)
enemy.grid_pos = new_pos
enemy_positions[new_pos] = enemy
```

Lookup is now O(1). A cell's occupancy check is a single dictionary key test:
```
if enemy_positions.has(target_pos): blocked
```

**The invariant:** `enemy_positions` must always exactly mirror the `enemies` array.
Every operation that changes an enemy's position or removes an enemy must update
both structures atomically. Bugs in this invariant cause phantom collisions
(enemies blocked by ghosts of dead enemies) or missing collisions (two enemies
occupying the same cell). This is the most common source of bugs in this system.

## 6. The Signal Graph — decoupling game logic from display

No display code reads game state directly on each frame. Instead, GameState emits
signals when state changes, and UI components subscribe to those signals.

```
player_action(dir)
  → GameState processes action
  → emits turn_ended
	  → DungeonView.queue_redraw()   (redraws tiles + entities)
	  → HUD._refresh()               (updates HP, floor labels)
  → emits message_added(text)
	  → MessageLog._on_message_added() (appends to log)
```

This architecture means:
- GameState has zero knowledge of how the dungeon is rendered.
- DungeonView has zero game logic — it only reads data and draws it.
- Adding a new UI element requires no changes to GameState.
- Unit-testing game logic requires no scene or renderer.

The rendering entry point is `_draw()` in DungeonView, called by the engine
after every `queue_redraw()`. It iterates all tiles and entities, reads their
current state from GameState, and draws colored rectangles + ASCII glyphs.
Since `_draw()` redraws everything from scratch each call, no incremental
update logic is needed — correctness is trivially guaranteed.

## Summary

| Algorithm             | Role                                        | Key property                             |
|-----------------------|---------------------------------------------|------------------------------------------|
| Room placement        | Generates a connected, explorable dungeon   | Overlap rejection + L-corridors          |
| Bresenham raycasting  | Determines what the player can see          | O(r³), two-layer visible/explored model  |
| Turn state machine    | Sequences actions in discrete time          | PLAYER → ENEMY → PLAYER loop             |
| Greedy chase AI       | Makes enemies feel threatening              | Chebyshev distance + priority fallback   |
| Spatial index dict    | O(1) occupancy queries                      | Must mirror entity array at all times    |
| Signal graph          | Decouples game logic from rendering         | Unidirectional data flow, Observer pattern |

These six structures are the complete algorithmic skeleton of a roguelike.
Every mechanic found in the genre — items, traps, multiple dungeon biomes,
boss encounters, persistent unlocks — is built on top of this foundation.

## File Structure

```
roguelike_template/
├── data/
│   ├── config.json        ← all game settings (tunable without code)
│   ├── strings_en.json    ← English UI strings
│   ├── strings_fr.json    ← French UI strings
│   └── enemies.json       ← enemy type definitions
├── autoloads/
│   ├── ConfigManager.gd   ← loads config.json, typed getters
│   ├── StringManager.gd   ← loads strings_<lang>.json, set_language(), language_changed signal
│   ├── EnemyDatabase.gd   ← loads enemies.json, get_type(id)
│   └── GameState.gd       ← state machine, turn loop, signals
├── scripts/               ← pure data/logic classes (no Node dependency)
│   ├── DungeonData.gd     ← grid + explored map
│   ├── DungeonGenerator.gd
│   ├── Entity.gd / PlayerEntity.gd / EnemyEntity.gd
│   ├── FOVSystem.gd
│   ├── CombatSystem.gd
│   └── AISystem.gd
└── scenes/
	├── Main.tscn / Main.gd
	└── ui/
		├── DungeonView.gd  ← pure renderer (_draw())
		├── HUD.gd          ← floor, HP, language button
		└── MessageLog.gd   ← rolling 5-line log
```

**Autoload order** (critical):
`ConfigManager → StringManager → EnemyDatabase → GameState`

## Editing Game Data

### config.json

| Key | Description |
|-----|-------------|
| `default_language` | `"en"` or `"fr"` — active language at startup |
| `dungeon_width / height` | Grid dimensions in tiles |
| `tile_size` | Pixel size of each tile |
| `max_rooms` | Maximum number of rooms per floor |
| `room_min_size / room_max_size` | Room dimension range |
| `fov_radius` | Player sight radius in tiles |
| `total_floors` | Number of floors before victory |
| `player_hp_max / attack / defense` | Player base stats |
| `enemies_per_room_min/max` | Enemy spawn count per room |
| `colors.*` | Hex color overrides for every tile and entity type |

### enemies.json

| Field | Description |
|-------|-------------|
| `id` | Unique string identifier |
| `display_name` | Shown in combat messages |
| `glyph` | Single character rendered on the map |
| `color` | Hex color (without `#`) |
| `hp / attack / defense` | Combat stats |
| `chase_range` | Chebyshev distance at which the enemy starts chasing |

### Adding a language

1. Copy `data/strings_en.json` → `data/strings_<code>.json`
2. Translate every value (keys must stay identical).
3. Add the new code to the `langs` array in `HUD.gd → _on_lang_button_pressed()`.

Any key missing in the new file automatically falls back to the English string —
partial translations are safe at runtime.
